1. Во внешнем чате кратко изложите или вставьте **ваш бизнес-контекст** (рынок, районы, гранты, персоны, ограничения).

3. Сохраните **ответ ассистента** как новый файл в репозитории, например: `GPT UI/docs/issue-interview-functional-spec-<дата>.md`, и отредактируйте под финальную версию.
4. Сверьте выход с чеклистом в конце этого файла.

## Промпт для ассистента

*(начало копирования)*

---

Ты — аналитик требований и автор функциональных спецификаций для продуктового ИИ-слоя. Ниже контекст продукта и жёсткие ограничения. После моего сообщения с **бизнес-контекстом** (или если он уже есть выше в переписке — используй его) ты должен выдать **один документ на Markdown** без лишней преамбулы: это **функциональная постановка задачи** для системы, где **GPT ведёт интервью-ингест** и в итоге готовит структурированные данные уровня **Issue** для прототипа **DOGEstonia** (Smart City / Эстония, грант).

### Продуктовый контекст (фиксировано)

- **Цель продукта:** bottom-up сбор **идей, желаний и жалоб** жителей с ориентацией на **цифровой контур** и дальнейшую обработку (нода, при необходимости токенизация / постоянное хранение). Гос-интеграция и compliance — в зоне ответственности прототипа; детали уточняются из моего бизнес-контекста.
- **Поток данных (референс):** GPT UI (инструкции, JSON, rulebook) → node (FastAPI) → смарт-контракты (где уместно) → Arweave-uploader → wallet. GPT **не** является источником истины по финальным статусам после записи в backend: только оркестратор и подготовка данных.
- **Доменная сущность интервью:** **Issue** (мысленная аналогия с JIRA-issue: тип, статус, метки, нарратив). Донорский legacy-контур в постановке **не используем** как домен; инвайты и соцтокеномика донора — вне обязательного ядра.
- **Критическое требование к интервью:** интервью **не является заполнением формы**. Оно задумано как **глубокий проход**: мягкое выявление того, что люди **не произносят с первого ответа** — их **желания, образы желаемого общественного пространства, претензии и жалобы** по отношению к **городу или выбранному району** (масштаб уточнить из моего контекста). Разрешены уточняющие, открытые и «проходные» вопросы, но без претензии на клиническую психотерапию; границы безопасности и этики задать явно в документе.

### Технический контракт выхода (дашборд SPA)

Интервью должно **собрать достаточно материала**, чтобы после нормализации на ноде объект **Issue** соответствовал ожиданиям UI (как в демо-моках). Обязательные поля для карточки и деталей:

| Поле | Требование |
|------|------------|
| `id` | Можно описать как генерируемый нодой; в спецификации укажи правило именования или placeholder. |
| `status` | Одно из: `NEW`, `VERIFIED`, `IN_REVIEW`, `ARCHIVED`. Для **только что завершённого интервью** зафиксируй ожидаемое значение по умолчанию (обычно `NEW`), если мой контекст не задаёт иное. |
| `type` | Одно из: `complaint`, `observation`, `absurdity`, `system_bug`. Опиши **правила классификации** из нарратива интервью. |
| `labels` | Массив строк (ключи тегов). Перечень допустимых labels и правило маппинга из ответов респондента — из моего контекста и здравого смысла; новые ключи согласовать с фильтрами UI. |
| `title` | Объект `{ et, ru, en }` — заголовок для дашборда. |
| `summary` | Опционально, `{ et, ru, en }` — кратко для карточки; если нет, UI падает на `title`. |
| `description` | Объект `{ et, ru, en }` — полный нарратив для страницы деталей (может собираться из интервью и сжатия). |

Опционально в той же спецификации опиши использование полей `institution` (`{ et, ru, en }`), `created_at`, `arweave_txid`, `image_txid`, `image_hash` (**не** предлагать фиктивные txid).

Дополнительно, **если уместно по моему контексту**, опиши наполнение или маппинг **IssueIntakePayload** из доменных типов SPA (например `severity`, `impact_estimation`, `problem_status`, `location`, `problem_categories`) — **без** навязывания PII; явно укажи, собираем ли идентифицирующие данные или только псевдоним/отсутствие идентификатора.

### Слой политики и валидации (замена «Kоны Рода»)

Задай требования к отдельному **документу validation / gate rules**: недопустимые темы, остановка интервью по safety, случаи `needs_clarification`, коды причин отказа при допуске к отправке на ноду. Если в моём контексте rulebook ещё нет — выведи **черновое оглавление** и список открытых вопросов ко мне как к оператору.

### Структура результирующего Markdown (строго соблюдай заголовки)

Выведи документ со следующей структурой:

```markdown
# DOGEstonia — функциональная постановка: GPT-интервью → Issue (SPA)

## 1. Назначение и границы
## 2. Персоны и контекст (из бизнес-диалога оператора)
## 3. Философия интервью: глубина vs форма
### 3.1. Принципы выявления желаний и жалоб (город / район)
### 3.2. Что не делаем (анкета, необоснованные обещания гос-ответа, сбор PII без явной политики)
## 4. Фазы диалога и критерии «достаточно данных»
## 5. Маппинг: ответы респондента → поля Issue (+ опционально IssueIntakePayload)
## 6. Классификация: type, labels, institution (правила и примеры)
## 7. Многоязычие (et / ru / en): политика заполнения и fallback
## 8. Policy gate / validation rules (требования к normative-документу или черновик правил)
## 9. Safety, GDPR, несовершеннолетние — границы для GPT
## 10. Стык с архитектурой: ingest-validation, normalizer, orchestrator (текстом, без выдуманных URL API)
## 11. Критерии приёмки (проверяемые формулировки)
## 12. Открытые вопросы к оператору
```

Пиши **конкретно**, без воды. Не выдумывай юридические нормы — если не уверен, вынеси в §12. Не утверждай, что обращение «принято ведомством», если это не подтверждено backend. Язык документа: **русский** (термины Issue, SPA, JSON — допускаются).

## Чеклист приёмки для оператора

После получения MD от внешнего ассистента проверь:

- [ ] Явно описана **глубина интервью** (не форма) и связь с **городом/районом**.
- [ ] Есть **фазы** и условие завершения сбора.
- [ ] Таблица или эквивалент: **какие ответы → какие поля Issue** (включая `title`/`summary`/`description` как `{ et, ru, en }`).
- [ ] Заданы правила **`type`** и **`labels`** (хотя бы черновик).
- [ ] Указан ожидаемый **`status`** новой записи для дашборда, если применимо.
- [ ] Есть раздел **gate / validation** и **safety / PII**.
- [ ] Нет противоречий с `docs/DOGEstonia.md` (GPT не SoT финальных статусов публикации).
- [ ] Опциональные on-chain поля — только с пометкой «после ноды / без фиктивных txid».
