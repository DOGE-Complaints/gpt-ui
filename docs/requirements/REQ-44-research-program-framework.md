# REQ-44: Research Program Framework — персонализированный доступ, согласие и расширенный сбор данных фокус-группы

> **Назначение:** предоставить DOGEstonia универсальный функциональный механизм исследовательских программ, через который выбранные зарегистрированные пользователи получают специальную роль, персонализированный код подтверждения и возможность явно согласиться на расширенный сбор данных, связанных с формированием историй в GPT.
>
> Первая программа на базе этого механизма — **Focus Group Program**.
>
> Участие позволяет DOGEstonia сохранять не только финальную историю, но и относящийся к ней процесс: релевантные фрагменты диалога, промежуточные структуры, уточняющие вопросы, изменения интерпретации, split/merge events, точки незаполненности, исследовательские наблюдения и метрики работы GPT-интервью.
>
> Сбор действует до ручного отключения участия. Пользователь может запросить прекращение участия и, отдельно, удаление ранее собранных исследовательских данных.

**Источник:** продуктовое интервью по Focus Group Mode / Research Program Framework, июль 2026; решение перейти от узкой функции фокус-группы к расширяемой модели `Research Program → Cohort → Role → Consent → Session → Dataset`.

**Версия:** 1.0 · 2026-07-11
**Статус:** Product Requirement Ready
**Приоритет:** P1 — необходим для контролируемого сбора обучающих, UX- и диагностических данных до масштабирования story-intake
**Тип:** Cross-layer functional requirement — GPT interaction + user role/consent state + research data collection + administrative scripts
**Серверная сторона:** требует поддержки ролей, персонализированных кодов, согласий, исследовательских сессий, связанных данных и удаления данных
**GPT-модуль:** требует определения research state пользователя, одноразовой валидации согласия и расширенного логирования story-related процесса
**Административный интерфейс:** отдельный UI не обязателен для MVP; операции могут выполняться скриптами
**Парные REQ:**

* REQ по Multi-Story Conversation & Independent Story Submission — несколько историй и story candidates внутри одного диалога;
* будущий REQ по Story Versioning & Post-Submission Updates — `Pending Update` и обновление уже отправленной истории;
* существующие требования story-interview, story normalization, submission handoff и privacy/data retention.

---

## 1. Проблема

Обычный процесс story-intake сохраняет преимущественно итоговый структурированный результат.

Этого недостаточно для системного улучшения GPT-модуля, потому что итоговая история не показывает:

* как пользователь первоначально формулировал опыт;
* какие части истории GPT распознал сразу;
* какие уточнения оказались полезными;
* какие вопросы были проигнорированы;
* какие поля оставались незаполненными;
* где GPT ошибся в классификации или структуре;
* когда одна история была ошибочно воспринята как несколько;
* когда несколько историй были ошибочно объединены;
* как менялась структура истории во время интервью;
* на каком этапе пользователь прекращал взаимодействие;
* насколько эффективно GPT проводил интервью;
* какие паттерны требуют изменения инструкций, таксономии или UX.

Одновременно такой расширенный сбор нельзя применять ко всем пользователям без явного согласия.

Требуется контролируемый механизм, который:

1. применяется только к заранее выбранным зарегистрированным пользователям;
2. связывает участие с их пользовательскими аккаунтами;
3. получает отдельное подтверждение расширенного сбора данных;
4. хранит версию согласия;
5. прекращает сбор по запросу;
6. позволяет удалить ранее собранные исследовательские данные;
7. остаётся расширяемым для будущих исследовательских программ.

## 2. Продуктовые принципы

### 2.1 Явное участие

Расширенный исследовательский сбор включается только для пользователей, которым назначена соответствующая исследовательская роль и которые подтвердили участие персонализированным кодом.

### 2.2 Код подтверждает согласие, а не является сильной аутентификацией

Персонализированный код не предназначен для защиты критически важных операций.

Его функции:

* подтвердить, что приглашение дошло до нужного участника;
* связать согласие с зарегистрированным аккаунтом;
* зафиксировать добровольное участие;
* активировать расширенный сбор данных.

Основная идентификация пользователя уже обеспечивается его регистрацией и авторизацией в DOGEstonia.

### 2.3 Сбор ограничен контекстом историй

Даже для участника исследовательской программы система не должна сохранять весь разговор без разбора.

Сохраняются только:

* сообщения и фрагменты, относящиеся к создаваемым историям;
* работа GPT по структурированию этих историй;
* исследовательские события и метрики story-intake.

Нерелевантный small talk и посторонние темы не должны включаться в исследовательский dataset.

### 2.4 История остаётся главным объектом исследования

Расширенные данные собираются вокруг конкретных историй и процесса их формирования.

Research Program Framework не создаёт универсальную абстрактную рабочую память GPT и не заменяет Web2/Web3 intelligence DOGEstonia.

### 2.5 Прозрачность

Участник должен понимать:

* что он входит в исследовательскую программу;
* какие категории данных собираются;
* как долго продолжается участие;
* как прекратить участие;
* как запросить удаление данных.

### 2.6 Отзыв участия не должен быть сложным

Для MVP достаточно возможности ответить на письмо-приглашение с запросом:

* остановить дальнейший сбор;
* остановить сбор и удалить ранее собранные исследовательские данные.

Администратор выполняет запрос через скрипт или ручную административную операцию.

### 2.7 Расширяемая модель ролей и программ

Focus Group — первая реализация, а не отдельная одноразовая конструкция.

Модель должна позволять позже добавлять другие программы, роли, когорты и версии согласий без изменения основного функционального контракта.

## 3. Текущее состояние

### 3.1 Нет формализованной исследовательской роли

Система не имеет согласованного функционального механизма, который отличает обычного пользователя от участника исследования story-intake.

### 3.2 Нет персонализированного кода согласия

Отсутствует отдельный код, который:

* создаётся для конкретного зарегистрированного пользователя;
* валидируется в контексте его аккаунта;
* подтверждает исследовательское согласие;
* активирует расширенный сбор данных.

### 3.3 Нет версионированного research consent

Булевого значения `consent = true` недостаточно.

Без версии соглашения невозможно определить:

* с каким текстом согласился пользователь;
* какой набор данных разрешалось собирать;
* действовало ли согласие на момент конкретной сессии.

### 3.4 Нет Research Session и Interview Trace

Обычная история не содержит полного пути своего формирования.

Не фиксируются системно:

* промежуточные версии;
* вопросы GPT;
* ответы пользователя;
* полезность вопросов;
* незаполненные поля;
* story split/merge events;
* пользовательские исправления;
* точки прекращения интервью.

### 3.5 Нет управляемого прекращения участия

Отсутствует единый функциональный процесс:

* отключения research role;
* прекращения будущего сбора;
* удаления ранее собранных исследовательских данных.

## 4. Целевое состояние

DOGEstonia поддерживает универсальную модель:

```text
Research Program
    ↓
Research Cohort
    ↓
Research Role
    ↓
Research Consent
    ↓
Research Session
    ↓
Research Dataset
```

Первая конфигурация:

```text
Research Program:
Focus Group Program

Research Role:
Focus Group Participant
```

Пользовательский поток:

```text
Пользователь регистрируется
↓
Передаёт администратору email аккаунта
↓
Администратор назначает research role
↓
Система генерирует персонализированный код
↓
Пользователь получает письмо с кодом и условиями
↓
GPT определяет наличие роли без активного согласия
↓
GPT просит ввести код
↓
Код валидируется в привязке к текущему аккаунту
↓
Фиксируется версия согласия
↓
Активируется расширенный story-related research collection
↓
Сбор продолжается в будущих сессиях без повторного ввода кода
↓
Участие прекращается после ручного отключения или запроса пользователя
```

## 5. Основные функциональные сущности

### 5.1 Research Program

Логическая исследовательская программа, определяющая:

* цель исследования;
* разрешённые категории данных;
* действующую версию согласия;
* период или статус программы;
* связанные роли;
* связанные когорты;
* правила сбора и удаления данных.

Первая программа:

```text
Focus Group Program
```

### 5.2 Research Cohort

Опциональная группа участников внутри программы.

Примеры:

* friends;
* internal-team;
* municipality-pilot;
* ngo-pilot;
* parents;
* students;
* entrepreneurs;
* russian-speaking-residents;
* estonian-speaking-residents.

Cohort используется для аналитического сравнения и не требует сбора дополнительных персональных данных.

### 5.3 Research Role

Роль, назначенная зарегистрированному пользователю.

Минимальные роли на первом этапе:

```text
Admin
Focus Group Participant
```

Модель должна поддерживать добавление будущих ролей, например:

```text
Research Participant
Early Adopter
Internal Tester
Moderator
Researcher
Municipality Pilot Participant
NGO Pilot Participant
```

Назначение роли само по себе не активирует расширенный сбор без подтверждённого consent.

### 5.4 Personalized Access Code

Код, созданный для конкретного участника.

Код должен быть связан как минимум с:

* зарегистрированным пользователем;
* research program;
* research role;
* consent version;
* временем создания;
* статусом;
* опциональной cohort;
* опциональной campaign/source.

Код предназначен для первичного подтверждения участия.

После успешного подтверждения повторное введение кода в каждой сессии не требуется.

### 5.5 Research Consent

Запись о добровольном подтверждении расширенного сбора данных.

Consent должен содержать:

* пользователя;
* research program;
* consent version;
* дату и время подтверждения;
* способ подтверждения;
* использованный personalized code;
* статус consent;
* дату прекращения, если участие завершено;
* основание прекращения, если оно известно;
* признак запроса на удаление данных.

### 5.6 Research Session

Сессия взаимодействия участника с GPT, в которой активен research collection.

Research Session связывает:

* пользователя;
* research program;
* cohort;
* consent version;
* GPT instruction/prompt version, если доступна;
* одну или несколько историй;
* interview traces;
* research observations;
* session metrics.

### 5.7 Research Dataset

Совокупность разрешённых исследовательских данных, созданных в рамках Research Session.

Dataset может включать:

* story-related dialogue fragments;
* story draft evolution;
* interview traces;
* split/merge events;
* user corrections;
* unanswered questions;
* research observations;
* story/session/GPT metrics.

## 6. Назначение участников

### 6.1 Предварительная регистрация

До назначения Focus Group role пользователь должен:

* иметь зарегистрированный аккаунт DOGEstonia;
* иметь email, связанный с аккаунтом.

### 6.2 Идентификация по email

Для MVP администратор использует email пользователя как входной идентификатор назначения роли.

Email уже является частью пользовательского аккаунта и не считается отдельным полем исследовательского профиля.

### 6.3 Одиночное назначение

Администратор должен иметь возможность:

* передать один email;
* назначить роль;
* выбрать research program;
* опционально указать cohort;
* опционально указать campaign/source;
* сгенерировать персонализированный код.

### 6.4 Пакетное назначение

Администратор должен иметь возможность передать список email и пакетно:

* найти соответствующих зарегистрированных пользователей;
* назначить им research role;
* сгенерировать отдельный персонализированный код каждому;
* назначить общую program/cohort/campaign;
* получить результат обработки по каждому email;
* при необходимости инициировать отправку писем.

### 6.5 Частичные ошибки пакетной обработки

Ошибка по одному email не должна блокировать обработку остальных.

Результат должен различать как минимум:

```text
Role assigned and code generated
User not found
Role already assigned
Active consent already exists
Invalid email input
Code generation failed
Email delivery failed
```

### 6.6 Повторное назначение

Если роль уже существует:

* не должно создаваться дублирующее назначение;
* администратор должен получить понятный статус;
* новый код создаётся только при явной необходимости переиздания.

## 7. Персонализированный код

### 7.1 Привязка к пользователю

Код действителен только для пользователя, которому он назначен.

Если код вводится другим авторизованным пользователем, он не должен активировать consent.

### 7.2 Уровень защиты

Код не обязан соответствовать требованиям сильной аутентификации.

При этом система должна исключать случайное подтверждение чужого согласия.

Минимально код должен:

* быть достаточно различимым;
* не быть общим для всей группы;
* иметь однозначную привязку к пользователю и программе;
* поддерживать отключение;
* поддерживать переиздание.

### 7.3 Срок действия

Базовое продуктовое правило:

* код используется для первичного подтверждения;
* после успешного подтверждения его повторное использование не требуется;
* код перестаёт быть активным после подтверждения, отзыва или переиздания.

Если срок действия потребуется позднее, он может добавляться конфигурацией программы.

### 7.4 Неверный код

Если пользователь вводит неверный код:

* consent не активируется;
* расширенный сбор не начинается;
* GPT сообщает об ошибке без раскрытия чужих данных;
* пользователь может повторить ввод.

### 7.5 Код другого пользователя

Если код существует, но не связан с текущим аккаунтом:

* код считается недействительным в данном контексте;
* система не сообщает, кому он принадлежит;
* consent не активируется.

### 7.6 Переиздание кода

Администратор должен иметь возможность:

* деактивировать старый код;
* создать новый код;
* при необходимости повторно отправить приглашение.

Старый код после переиздания не должен активировать consent.

## 8. Email-приглашение

Письмо участнику должно содержать:

* название исследовательской программы;
* объяснение цели участия;
* персонализированный код;
* инструкцию, где и когда его ввести;
* описание собираемых категорий данных;
* указание, что сохраняются только story-related части диалога;
* указание, что участие продолжается до ручного отключения;
* способ прекратить участие;
* способ запросить удаление ранее собранных исследовательских данных;
* указание, что пользователь может ответить на это письмо с соответствующим запросом;
* ссылку или текст действующей версии соглашения;
* отсутствие обещаний относительно результатов поданных историй.

Пример смыслового блока:

> Участие позволяет DOGEstonia анализировать, как истории формируются в диалоге с GPT: какие уточнения помогают, где возникают ошибки и как улучшается структура истории. Мы собираем только те части разговора, которые относятся к создаваемым историям. Вы можете в любой момент ответить на это письмо и попросить прекратить участие или удалить ранее собранные исследовательские данные.

Финальный текст письма и юридическая редакция GDPR agreement могут оформляться отдельно.

## 9. Активация consent в GPT

### 9.1 Определение состояния пользователя

При авторизованном взаимодействии GPT-модуль должен различать состояния:

```text
No research role
Research role assigned, consent not confirmed
Research role assigned, active consent confirmed
Research role disabled
Consent withdrawn
Deletion requested
```

### 9.2 Первый вход после назначения роли

Если у пользователя есть Focus Group role, но нет подтверждённого consent, GPT должен:

1. сообщить о приглашении в исследовательскую программу;
2. кратко объяснить расширенный сбор;
3. предложить ознакомиться с соглашением;
4. попросить персонализированный код;
5. не начинать расширенный сбор до успешной валидации.

### 9.3 Успешная валидация

После успешной проверки кода система:

* связывает согласие с текущим пользователем;
* сохраняет consent version;
* фиксирует дату и способ подтверждения;
* активирует research participation;
* отмечает код использованным;
* сообщает пользователю об успешной активации.

### 9.4 Повторные сессии

При активном consent:

* повторный код не запрашивается;
* GPT может сразу работать в research collection mode;
* каждая Research Session связывается с действующим consent.

### 9.5 Обновление текста соглашения

Если появляется новая версия соглашения, необходимость повторного подтверждения определяется политикой программы.

Система должна позволять различать:

```text
Consent v1 remains valid
Consent v2 requires re-consent
Consent v2 applies only to new participants
```

Если повторное согласие обязательно, расширенный сбор по новым правилам не должен начинаться до подтверждения новой версии.

## 10. Границы расширенного сбора

### 10.1 Что сохраняется

Для участника с активным consent система может сохранять:

* финальные структурированные истории;
* пользовательские сообщения, относящиеся к историям;
* релевантные части сообщений, содержащих одновременно story-related и посторонний контент;
* вопросы GPT, связанные со сбором истории;
* ответы пользователя на такие вопросы;
* исходный фрагмент, из которого возникла история;
* промежуточные структуры истории;
* последовательность изменений полей;
* изменения классификационных гипотез;
* пользовательские исправления понимания GPT;
* story split events;
* story merge events;
* связь вопросов с заполненными полями;
* проигнорированные вопросы;
* повторно заданные вопросы;
* незаполненные поля;
* точки прекращения интервью;
* метрики эффективности интервью;
* исследовательские наблюдения GPT.

### 10.2 Что не сохраняется

Research collection не должен сохранять:

* нерелевантный small talk;
* разговоры, не связанные с создаваемыми историями;
* посторонние вопросы пользователя;
* дополнительные персональные данные, не необходимые для истории или исследования процесса;
* отклонённые GPT гипотезы как отдельные story objects;
* внутреннюю универсальную chain-of-thought или скрытые рассуждения модели;
* данные после прекращения consent.

### 10.3 Смешанное сообщение

Если одно пользовательское сообщение содержит:

* story-related фрагмент;
* посторонний фрагмент,

система должна сохранить только релевантную часть или маркировать границы релевантного контента.

### 10.4 Отклонённый story candidate

Отклонённый пользователем кандидат:

* не становится отдельной финальной историей;
* может быть отражён в Research Trace как событие отклонения;
* не должен храниться как самостоятельный civic story object.

---

## 11. Эволюция истории

Для каждой истории в исследовательской сессии система должна позволять восстановить процесс её формирования.

Минимально отслеживаются:

* первый story-related fragment;
* первоначальная гипотеза структуры;
* промежуточные версии;
* добавленные поля;
* изменённые поля;
* удалённые или исправленные значения;
* изменения topic/category/region и других интерпретаций;
* открытые вопросы;
* финальная версия перед подтверждением;
* результат подачи или отказа от подачи.

Промежуточные версии являются исследовательскими данными и не заменяют canonical final story.

---

## 12. Interview Trace

### 12.1 Назначение

Interview Trace показывает, как GPT и пользователь совместно сформировали историю.

### 12.2 Состав события интервью

Для каждого релевантного вопроса GPT должно быть возможно определить:

* к какой истории он относился;
* зачем вопрос был задан;
* какое поле или неопределённость он проверял;
* ответил ли пользователь;
* добавил ли ответ новую информацию;
* какие поля были заполнены или изменены;
* был ли вопрос проигнорирован;
* был ли он повторён;
* было ли интервью продолжено после вопроса;
* мог ли вопрос стать точкой прекращения взаимодействия.

### 12.3 Полезность вопроса

Система должна позволять позже оценивать вопросы по продуктовой полезности.

Примеры:

```text
Question filled one required field
Question filled several fields
Question clarified story separation
Question caused user correction
Question produced no new information
Question was ignored
Question was repeated
User stopped interacting after question
```

Оценка может быть вычисляемой или сохраняться как набор событий; конкретный аналитический алгоритм находится вне scope этого Functional Requirement.

---

## 13. Story Split и Merge Events

### 13.1 Split Event

Split Event фиксируется, когда:

* GPT первоначально воспринимал материал как одну историю;
* затем определил, что он содержит несколько независимых историй;
* либо пользователь явно потребовал разделить материал.

Должны быть доступны:

* исходный общий draft;
* момент разделения;
* причина;
* инициатор: GPT или пользователь;
* возникшие story candidates;
* подтверждение или коррекция пользователя.

### 13.2 Merge Event

Merge Event фиксируется, когда:

* GPT создал несколько кандидатов;
* пользователь или последующий анализ показал, что это одна причинно связанная история.

Должны быть доступны:

* исходные candidates;
* причина объединения;
* инициатор;
* итоговый story draft.

### 13.3 Исследовательская ценность

Split/Merge events используются для:

* настройки multi-story logic;
* оценки ошибок GPT;
* улучшения инструкции;
* настройки порогов и весов story separation;
* анализа пользовательского понимания границ истории.

---

## 14. Research Observations

### 14.1 Назначение

GPT может сохранять наблюдения о качестве процесса, не являющиеся частью пользовательской истории.

Примеры:

* пользователь несколько раз пытался начать вторую историю, но GPT возвращался к первой;
* пользователь не понял формулировку вопроса;
* GPT слишком рано предложил классификацию;
* пользователь исправил неверно определённую сферу;
* пользователь прекратил отвечать после серии уточнений;
* пользователь испытывал сложности с определением участников;
* GPT повторно запросил уже предоставленную информацию.

### 14.2 Ограничения

Research Observation:

* не включается в canonical story;
* не является утверждением о личности пользователя;
* не должно содержать ненужные диагнозы или психологические интерпретации;
* описывает наблюдаемое взаимодействие и функциональную проблему;
* связывается с session и, если применимо, со story.

---

## 15. Метрики

Система должна собирать максимально широкий набор полезных метрик, если они формируются из разрешённых story-related данных и не требуют избыточного сбора персональных данных.

### 15.1 User-level metrics

* количество research sessions;
* количество начатых историй;
* количество отправленных историй;
* среднее количество историй за сессию;
* частота возвращения;
* средняя длина story-related ответа;
* частота исправления GPT;
* средняя полнота историй;
* частота отказа от кандидатов;
* изменение поведения пользователя между сессиями.

### 15.2 Session-level metrics

* начало и завершение сессии;
* продолжительность;
* количество релевантных сообщений;
* количество обнаруженных story candidates;
* количество завершённых историй;
* количество незавершённых историй;
* количество отправленных историй;
* количество отклонённых кандидатов;
* количество split/merge events;
* точка прекращения сессии;
* program/cohort/campaign;
* consent version;
* GPT instruction version, если доступна.

### 15.3 Story-level metrics

* время до первого story candidate;
* время до первого draft;
* время до состояния готовности;
* время до отправки;
* количество уточняющих вопросов;
* количество отвеченных вопросов;
* количество проигнорированных вопросов;
* количество повторных вопросов;
* количество изменений структуры;
* количество пользовательских исправлений;
* количество классификационных изменений;
* процент заполненности;
* количество split/merge events;
* факт подачи;
* факт отказа;
* причина незавершённости, если известна.

### 15.4 GPT interview metrics

* количество вопросов;
* среднее количество вопросов на историю;
* полезность вопросов;
* какие поля заполняются конкретными вопросами;
* вопросы без новой информации;
* вопросы, чаще других игнорируемые пользователями;
* повторяющиеся вопросы;
* ошибки распознавания story candidates;
* исправленные пользователем классификации;
* автоматически обнаруженные дополнительные истории;
* подтверждённые и отменённые split decisions;
* точки disengagement;
* эффективность разных версий инструкции.

### 15.5 Multi-session evolution metrics

Система должна позволять анализировать, как участник со временем осваивает story-intake:

* быстрее ли формулирует истории;
* требуется ли меньше уточнений;
* растёт ли полнота;
* чаще ли пользователь самостоятельно разделяет истории;
* уменьшается ли количество correction events.

Эта аналитика не должна превращаться в публичную оценку пользователя или ограничивать его возможности.

## 16. Cohort и Campaign

### 16.1 Cohort

Cohort используется для группировки участников по контексту исследования.

Присвоение cohort:

* опционально;
* не требует дополнительных персональных полей;
* может выполняться при назначении роли;
* может использоваться в агрегированной аналитике.

### 16.2 Campaign/Source

Campaign/source позволяет определить источник набора.

Примеры:

```text
focus-group-01
municipality-pilot
ngo-pilot
telegram-july
personal-invite
internal-testing
```

Campaign не является ролью и не влияет самостоятельно на разрешения пользователя.

---

## 17. Прекращение участия

### 17.1 Запрос пользователя

Пользователь может запросить:

1. прекращение будущего research collection;
2. прекращение участия и удаление ранее собранных исследовательских данных.

Для MVP запрос может поступать ответом на email-приглашение.

### 17.2 Отключение роли

Администратор через скрипт или административную операцию:

* отключает Focus Group role либо research participation;
* деактивирует consent;
* фиксирует дату прекращения;
* прекращает будущий расширенный сбор.

### 17.3 Немедленное действие

После деактивации:

* новые Research Sessions не создаются;
* story-related данные продолжают обрабатываться только в обычном режиме;
* GPT не должен сообщать, что research collection активен;
* ранее активный код не должен повторно включать участие без нового административного назначения.

### 17.4 Повторное включение

Повторное участие возможно только после:

* нового административного назначения или реактивации;
* нового consent, если этого требует политика программы;
* нового кода, если старый был отозван.

---

## 18. Удаление исследовательских данных

### 18.1 Отдельный флаг удаления

Отключение роли и удаление данных — разные операции.

Скрипт или административная команда должны поддерживать как минимум:

```text
Disable future research collection only
Disable collection and delete previous research data
```

### 18.2 Что подлежит удалению

При подтверждённом запросе на удаление должны удаляться или необратимо обезличиваться связанные с пользователем:

* Research Sessions;
* Interview Traces;
* промежуточные версии story drafts;
* Research Observations;
* research metrics;
* split/merge research records;
* cohort/campaign research associations;
* другие данные, созданные исключительно для исследовательских целей.

### 18.3 Финальные civic stories

Удаление финальных уже поданных историй не определяется автоматически этим REQ.

Причина:

* финальная история может существовать как отдельный продуктовый и протокольный объект;
* для неё могут действовать отдельные правила retention, receipts, Arweave и downstream processing.

При запросе удаления исследовательских данных система должна различать:

```text
Research-only data
Final submitted story data
Protocol/proof data
```

Правила удаления или обновления финальной истории должны быть определены отдельными requirements.

### 18.4 Производные агрегаты

Если данные уже включены в полностью агрегированную статистику, которая не позволяет идентифицировать пользователя, необходимость пересчёта определяется политикой данных.

MVP должен как минимум удалять все user-linked research records.

### 18.5 Результат удаления

Административная операция должна возвращать понятный результат:

* участие отключено;
* удаление выполнено;
* удаление частично выполнено;
* некоторые данные регулируются отдельной retention policy;
* ошибка удаления.

## 19. Административные операции MVP

Полноценный admin UI не обязателен.

MVP может использовать скрипты для:

### 19.1 Назначения

* назначить роль одному пользователю;
* назначить роль списку пользователей;
* выбрать program;
* выбрать cohort;
* выбрать campaign;
* сгенерировать коды;
* инициировать отправку email.

### 19.2 Проверки

* проверить research status по email;
* проверить active consent;
* определить consent version;
* проверить статус кода;
* получить program/cohort/campaign.

### 19.3 Отключения

* отключить участие;
* отозвать код;
* отозвать consent;
* отключить только будущий сбор;
* отключить и удалить research data.

### 19.4 Переиздания

* создать новый код;
* отменить предыдущий;
* повторно отправить приглашение.

## 20. Edge Cases

### 20.1 Email не найден

Если пользователь ещё не зарегистрирован:

* роль не назначается;
* код не создаётся;
* результат указывает `User not found`;
* система не создаёт фиктивного пользователя автоматически.

### 20.2 Пользователь зарегистрировался под другим email

Код, назначенный другому аккаунту, не активируется.

Администратор должен либо:

* назначить роль правильному аккаунту;
* либо отдельно решить вопрос смены email.

### 20.3 Пользователь получил роль, но не ввёл код

* research collection не активен;
* обычный story-intake остаётся доступным;
* GPT может напомнить о приглашении, но не должен блокировать основную функциональность.

### 20.4 Пользователь потерял код

Администратор может переиздать код.

### 20.5 Пользователь вводит код несколько раз

После успешного consent:

* повторный ввод не создаёт дублирующее согласие;
* GPT сообщает, что участие уже активно.

### 20.6 Пользователь отвечает на письмо с неоднозначной просьбой

Например:

> Я больше не хочу участвовать.

По умолчанию это означает:

* остановить будущий сбор;
* не удалять прошлые данные без отдельного запроса.

Удаление должно выполняться при явном запросе или после уточнения администратором.

### 20.7 Пользователь просит удалить всё

Система должна:

* отключить участие;
* запустить удаление research-only data;
* отдельно обозначить статус финальных submitted stories и protocol records.

### 20.8 Роль отключена посреди активной сессии

После получения обновлённого статуса:

* новый расширенный сбор прекращается;
* уже созданные буферные research records не должны продолжать накапливаться;
* обычный story-intake может продолжиться.

Точная транзакционная граница реализации определяется техническим дизайном.

### 20.9 Ошибка логирования research data

Ошибка расширенного research logging не должна автоматически блокировать основную подачу истории, если core story flow исправен.

При этом:

* ошибка фиксируется;
* данные не должны частично представляться как полный Interview Trace;
* система может отметить Research Session как incomplete.

### 20.10 Недоступность consent validation

Если код невозможно проверить:

* consent не считается подтверждённым;
* расширенный сбор не начинается;
* пользователь получает понятное сообщение;
* обычный story-intake остаётся доступным.

### 20.11 Один пользователь в нескольких программах

Модель должна допускать участие в нескольких Research Programs.

Consent и data scope должны определяться отдельно по каждой программе.

### 20.12 Изменение cohort

Изменение cohort не должно:

* отменять consent;
* создавать нового пользователя;
* менять уже сохранённую принадлежность исторических сессий.

Старые сессии сохраняют cohort, действовавшую на момент их создания.

### 20.13 Удаление роли без удаления consent record

Для аудита факта согласия consent record может сохраняться в минимальном юридически необходимом виде, даже если research dataset удалён.

Конкретный минимальный retention определяется юридической политикой и должен быть отделён от исследовательского контента.

## 21. Privacy и GDPR-рамка

### 21.1 Отдельное соглашение

Для Focus Group Program должен существовать отдельный GDPR-aligned agreement или privacy notice.

REQ-44 определяет функциональное использование соглашения, но не заменяет юридическую редакцию.

### 21.2 Содержание соглашения

Соглашение должно описывать:

* цель исследования;
* категории собираемых данных;
* связь данных с пользовательским аккаунтом;
* ограничение story-related контентом;
* возможный доступ исследователей DOGEstonia;
* использование данных для улучшения GPT, UX, таксономии, классификации и кластеризации;
* срок участия;
* способ прекращения;
* способ удаления данных;
* возможные ограничения удаления финальных submitted stories и protocol records;
* действующую версию документа.

### 21.3 Data minimization

Несмотря на расширенный режим, система должна:

* не собирать данные «на всякий случай» вне story-intake;
* не создавать дополнительные персональные профили;
* не добавлять данные, которых пользователь не предоставлял;
* не хранить нерелевантный разговор.

### 21.4 Доступ к research data

Доступ должен предоставляться только ролям, которым он требуется для исследования и улучшения продукта.

Первоначально это может быть Admin.

Будущая роль Researcher может быть добавлена отдельно.

---

## 22. Не в scope

* Декомпозиция REQ-44 на user stories или implementation tasks.
* Полноценный административный UI.
* Самостоятельная регистрация пользователя по invitation code.
* Сильная многофакторная аутентификация кодом.
* Публичная research analytics dashboard.
* Автоматическая генерация юридического текста GDPR agreement.
* Обучение модели непосредственно внутри этого requirement.
* Конкретные алгоритмы статистического анализа dataset.
* Multi-story intake logic — отдельный requirement.
* Story versioning и post-submission updates — отдельный requirement.
* Удаление или изменение blockchain/Arweave records.
* Универсальная Conversation Workspace architecture.
* Сбор полного диалога пользователя вне story-related контекста.

| GPT entry flow      | Запрос кода при наличии роли без active consent                                               |
| Consent             | Версионированная запись согласия                                                              |
| Research sessions   | Связь пользователя, consent, программы, историй и метрик                                      |
| Data collection     | Расширенный сбор только story-related данных                                                  |
| Interview trace     | Вопросы, ответы, заполненные поля, ignored/repeated/drop-off                                  |
| Story evolution     | Промежуточные структуры и изменения                                                           |
| Split/Merge         | Исследовательские события разделения и объединения                                            |
| Observations        | Отдельные продуктовые наблюдения GPT                                                          |
| Metrics             | User-, session-, story- и GPT-level metrics                                                   |
| Withdrawal          | Ручное/скриптовое прекращение участия                                                         |
| Deletion            | Отдельный режим удаления research-only data                                                   |

## 24. Acceptance Criteria

### 24.1 Research Program и роли

* [ ] Система поддерживает сущность Research Program.
* [ ] Создана или может быть настроена программа Focus Group Program.
* [ ] Система поддерживает расширяемую модель ролей.
* [ ] Минимально доступны роли `Admin` и `Focus Group Participant`.
* [ ] Роль назначается только существующему зарегистрированному пользователю.
* [ ] Назначение роли не активирует расширенный сбор до подтверждения consent.

### 24.2 Одиночное и пакетное назначение

* [ ] Администратор может назначить Focus Group role по одному email.
* [ ] Администратор может передать список email для пакетной обработки.
* [ ] Для каждого успешно найденного пользователя создаётся отдельный персонализированный код.
* [ ] Ошибка одного элемента не останавливает весь batch.
* [ ] Результат сообщает статус по каждому email.
* [ ] Повторное назначение не создаёт дублирующую роль.

### 24.3 Персонализированный код

* [ ] Код связан с конкретным пользователем.
* [ ] Код связан с Research Program.
* [ ] Код связан с consent version.
* [ ] Чужой код не активирует consent текущего пользователя.
* [ ] После успешного использования код не создаёт повторных consent records.
* [ ] Код можно отозвать.
* [ ] Код можно переиздать.
* [ ] Старый код после переиздания не действует.

### 24.4 Email-приглашение

* [ ] Письмо содержит персонализированный код.
* [ ] Письмо объясняет цель исследовательской программы.
* [ ] Письмо перечисляет основные категории собираемых данных.
* [ ] Письмо указывает, что сохраняются только story-related части диалога.
* [ ] Письмо объясняет, что участие продолжается до ручного отключения.
* [ ] Письмо объясняет способ прекратить участие.
* [ ] Письмо объясняет способ запросить удаление данных.
* [ ] Пользователь может использовать ответ на письмо как канал запроса.

### 24.5 Consent flow

* [ ] GPT различает role assigned и active consent.
* [ ] При роли без consent GPT просит персонализированный код.
* [ ] До успешной валидации расширенный сбор не начинается.
* [ ] Успешный код создаёт consent record.
* [ ] Consent record содержит версию соглашения.
* [ ] Consent связан с текущим пользователем и Research Program.
* [ ] В будущих сессиях код повторно не запрашивается при активном consent.
* [ ] Сессия связывается с действующей consent version.

### 24.6 Data scope

* [ ] Сохраняются только story-related пользовательские фрагменты.
* [ ] Сохраняются story-related вопросы GPT.
* [ ] Нерелевантный small talk не включается в Research Dataset.
* [ ] Смешанные сообщения ограничиваются релевантными фрагментами.
* [ ] Не создаётся универсальная запись полного диалога.
* [ ] Не сохраняется скрытая chain-of-thought модели.

### 24.7 Story evolution и Interview Trace

* [ ] Сохраняется первый raw story fragment.
* [ ] Сохраняются промежуточные структуры истории.
* [ ] Сохраняются изменения полей.
* [ ] Сохраняются пользовательские исправления.
* [ ] Каждый релевантный вопрос может быть связан с целевым полем или неопределённостью.
* [ ] Фиксируется, был ли вопрос отвечен, проигнорирован или повторён.
* [ ] Фиксируется, какие поля были заполнены ответом.
* [ ] Поддерживается отметка потенциальной точки disengagement.

### 24.8 Split/Merge и Research Observations

* [ ] Поддерживается Story Split Event.
* [ ] Поддерживается Story Merge Event.
* [ ] События содержат исходные и результирующие candidates/drafts.
* [ ] Фиксируется инициатор события.
* [ ] GPT может создавать Research Observations.
* [ ] Research Observation не включается в canonical story.
* [ ] Research Observation описывает наблюдаемое продуктовое поведение, а не неподтверждённые личностные характеристики.

### 24.9 Metrics

* [ ] Собираются session-level metrics.
* [ ] Собираются story-level metrics.
* [ ] Собираются GPT interview metrics.
* [ ] Собираются user-level research metrics.
* [ ] Метрики связаны с program, cohort, consent version и, если доступно, GPT instruction version.
* [ ] Метрики не используются для ограничения прав пользователя.

### 24.10 Прекращение участия

* [ ] Администратор может отключить research participation.
* [ ] После отключения новые Research Sessions не создаются.
* [ ] После отключения расширенный сбор прекращается.
* [ ] Обычный story-intake остаётся доступным.
* [ ] Старый код не может самостоятельно повторно активировать участие.
* [ ] Повторное участие требует новой разрешённой активации.

### 24.11 Удаление данных

* [ ] Отключение будущего сбора и удаление прошлых данных являются разными операциями.
* [ ] Административная операция поддерживает флаг удаления.
* [ ] При удалении удаляются user-linked Research Sessions.
* [ ] Удаляются Interview Traces.
* [ ] Удаляются промежуточные drafts и Research Observations.
* [ ] Удаляются user-linked research metrics.
* [ ] Финальные submitted stories обрабатываются по отдельной policy/requirement.
* [ ] Результат удаления сообщает о полном, частичном или неуспешном выполнении.

### 24.12 Resilience

* [ ] Ошибка research logging не блокирует core story submission, если основной flow работает.
* [ ] Недоступность code validation не активирует consent по умолчанию.
* [ ] Недоступность code validation не блокирует обычный story-intake.
* [ ] Частичная ошибка batch assignment не отменяет успешные назначения.
* [ ] Неполная Research Session обозначается как incomplete, а не как полный dataset.

## 26. Краткая формула

```text
Selected registered user
↓
Research role
↓
Personalized code
↓
Versioned consent
↓
Story-related extended collection
↓
Interview Trace + Story Evolution + Metrics
↓
Product improvement
```

При этом:

```text
No consent
→ no extended research collection

Consent withdrawn
→ future collection stops

Deletion requested
→ user-linked research data is removed

Final civic stories
→ governed separately
```
