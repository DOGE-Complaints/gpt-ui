# REQ-18: Формат handoff GPT → API (Story Intake) и связка с Module 1

> **Назначение:** зафиксировать **требования уровня продукта** к тому, что Custom GPT / оркестратор должен выдавать для приёма истории и downstream-слоёв, в **полном соответствии** с контрактом Module 2.  
> **Авторитетный технический SoT (HTTP-поля, примеры JSON, коды ошибок):**  
> `doge-complaints-gateway/docs/requirements/19-inbound-api-gpt-preprocessing-and-spa-issue-contracts.md` (**§19**).  
> При расхождении между этим REQ и §19 приоритет у **§19**; REQ-18 задаёт обязательность для GPT и трассировку к **REQ-01…18** (включая связанные FR из REQ-09).

**Версия:** 0.1 · 2026-04-19  
**Статус:** активный draft, синхронизирован с §19 (включая `schema_version` `m2.story_intake_envelope.v1`).

---

## 1. Устаревшая модель (явно out of scope)

Следующее **не** является целевым описанием handoff для DOGEstonia в связке с Story Store / Distinct Issue:

- Подача в API **только** плоского объекта карточки без **immutable narrative** и без разделения «user said / system inferred».
- Использование legacy-домена донора как целевого контракта приёма; см. **FR-M1-035** (REQ-09).
- Утверждение финальных **`id`**, **on-chain txid**, **витринного статуса** как факта без ответа API (**FR-M1-038**).

Целевая модель: **Story-first**; issue на витрине — **производный** объект; GPT передаёт **черновики и сигналы** (см. §2 §19 и таблицу принципов ниже).

---

## 2. Принципы интеграции (обязательны)

| Принцип | Требование к GPT / инструкциям |
|--------|----------------------------------|
| Story-first | Первичен рассказ пользователя; проекция в issue-карточку — следствие. |
| GPT не SoT управления | Статусы публикации, финальный production `id`, принятие в кластер — только система; в handoff — черновики и сигналы. |
| Разделение правды и интерпретации | Дословное — в `narrative` / `live_story_context`; интерпретации и нормализованные сигналы — в `structured_signals` и `spa_issue_draft`. |
| SPA zero-change (MVP) | Блок `spa_issue_draft` совместим с `ISSUE_TYPE`, i18n `{ et, ru, en }`, словарями labels — как **SPA / mock-guide**; типы — из согласованного словаря (см. `spa-app/src/domain/types.js`). |
| Идемпотентность | Для реальных отправок использовать стабильный **`Idempotency-Key`** (см. §3 §19). |
| PII minimization | Не раздувать персональные данные; использовать `privacy` при риске PII. |
| OAuth пользователя vs сервисный канал | Пользовательский субъект — в **`submitter.external_user_id`**; доверие к вызову — заголовок **`Authorization`** (сервисная аутентификация). Не путать уровни. |

## 3. Два связанных «выхода» GPT (без противоречия REQ)

| Контур | Назначение | Типичный артефакт / wire |
|--------|------------|---------------------------|
| **Module 1 — Issues Actions (узел)** | Черновик Issue по строгой цепочке инструкций | Логически `normalized_issue_payload` → HTTP тело **`IssueDraftCreateRequest`** (`GPT UI/docs/custom-gpt-issues-reference.openapi.yaml`). |
| **Module 2 — Story Intake** | Полный пакет истории + авторство + сигналы для аналитики и проекции | **`StoryIntakeEnvelope`** в теле `POST` (логический контракт §4 §19). |

**Требование:** инструкции и операторские чеклисты должны **не смешивать** проверку успеха по Issues OpenAPI с проверкой успеха по Story Intake; при необходимости оба контура документируются в приёмке (**REQ-14**) как разные слои (см. также `GPT UI/docs/analysis/doc19-inbound-api-audit-vs-gim33-41-gap-closure-tasks.md`).

## 4. Транспорт HTTP (логический контракт)

Соответствие **§3 §19**:

| Элемент | Требование |
|---------|------------|
| Метод | `POST` |
| `Content-Type` | `application/json` |
| `Authorization` | Сервисная аутентификация канала (Bearer / иное по EPIC-M2-09); не подменяет `submitter`. |
| `Idempotency-Key` | Рекомендуется как обязательный для GPT для сабмита истории. |
| `X-Request-Id` | Опционально. |

Реальный path версионируется на стороне gateway (например `/v1/stories/intake`).

## 5. Корень тела: `StoryIntakeEnvelope`

Обязательно в каждом запросе:

- **`schema_version`** — строка версии конверта; текущая опорная: **`m2.story_intake_envelope.v1`** (§21 §19).

Обязательно по смыслу приёма истории:

- **`narrative`** — неизменяемое первичное свидетельство (**минимум** `original_text` после trim).

Настоятельно рекомендуется для продуктового потока с логином:

- **`submitter`** с **`external_user_id`** (opaque) и по возможности **`identity_issuer`**.

Настоятельно рекомендуется для GPT:

- **`live_story_context`** (многоходовый диалог, факты, confidence по фактам);
- **`spa_issue_draft`** — сухой SPA-черновик с полным **i18n** для `title` / `summary` / `description`.

Опциональные блоки: **`structured_signals`**, **`location`**, **`time`**, **`origin`**, **`privacy`**, **`client`**, **`gov_interop_hints`**.

Полная структура полей, типы и правила валидации — **§4–§15, §18–§23 §19**.

## 6. Блок `narrative` (обязательный)

| Поле | Смысл |
|------|--------|
| `original_text` | Полный дословный текст (можно склейка реплик с маркерами). |
| `language` | BCP-47, опционально. |
| `title_hint` | Не финальный title карточки. |
| `locale_preferences` | Опционально для downstream i18n. |

**Требование:** бэкенд не перезаписывает `original_text` как «истину пользователя» (§6 §19).

---

## 7. Блоки интерпретации и контекста

- **`structured_signals`** — переформулировки, `deep_need`, `desired_state`, темы, hints типа сбоя и т.д. (§7 §19). Не заменяют `original_text`.
- **`live_story_context`** — диалоговые реплики, уточнения, `key_facts` с `evidence_quote` и **`confidence`**, сущности, медиа-ссылки, `consistency_notes` (§8 §19).

Связь с **REQ-10:** слои 10.1–10.4 логически питают содержание **`structured_signals`** и поля **`spa_issue_draft`**; слой **10.6** должен быть согласован с `key_facts[].confidence`, `spa_issue_draft.confidence` и честной маркировкой неполноты.

---

## 8. Блок `spa_issue_draft` (SPA-совместимый черновик)

Соответствие **§14 §19** (подпункты 13.x в исходном документе gateway):

- Обязательные для заполнения GPT при наличии блока: согласованные **`type`**, **`labels`**, **`title`**, **`summary`**, **`description`** в форме **`i18n_text`** (`et`, `ru`, `en` — все ключи обязательны; fallback по политике продукта).
- Рекомендуемые мета-поля: **`draft_provenance`** (`gpt_preprocess_v1`), **`confidence`** (0…1).
- **`id` / `status`** на черновике могут быть переопределены сервером; не считать финальными без ответа API.
- **Запрещены** фиктивные **`arweave_txid` / `image_txid`** (только реальные интеграционные значения).

**Связь с Module 1:** логические поля карточки согласованы с `GPT UI/instructions/story-data-model.md` §4.1 и нормализатором (`normalized_issue_payload.canonical_payload`); расширенный **envelope** §19 добавляет narrative, авторство, гео/время, гос-hints — вне минимального Issues OpenAPI.

## 9. `time`, `location`, `origin`, `privacy`, `client`, `gov_interop_hints`

Копировать семантику и поля из **§9–§12, §15 §19** (включая маппинг **`time.kind`** к проекции **`ISSUE_TIME_TYPE`** на стороне SPA — см. таблицу в §19 после блока `time`).

**`origin`:** связь с OpenAI (`conversation_id`, `tool_call_id`, `submitted_at`, …) — для lineage и идемпотентности; не смешивать с **`submitter`**.
